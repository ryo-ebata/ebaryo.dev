## はじめに

2025年から2026年にかけて、AIコーディングエージェントのエコシステムが急速に拡大しました。

Claude Code、Cursor、Windsurf、GitHub Copilotといったツールが開発現場に浸透し、MCPサーバーやスキル、フックといった拡張機能が日々生み出されています。awesome-claude-codeのようなキュレーションリポジトリには数百のサードパーティ製アーティファクトが並び、開発者は気軽にそれらをインストールしています。

私もそのひとりでした。

便利そうなスキルを見つけてはインストールし、フックを設定し、MCPサーバーを接続する。その過程で、ふと立ち止まったことがあります。「このSKILL.md、中身をちゃんと読んだか？」と。

読んでいませんでした。

この経験が、cc-auditを作るきっかけになりました。

https://github.com/ryo-ebata/cc-audit

## なぜ「エージェントのスキル」が危険なのか

MCPサーバーのセキュリティリスクについては、2025年後半から多くの議論がなされてきました。CVE-2025-6514ではmcp-remoteのOAuth検証不備により約43万7千の開発環境が影響を受け、2025年9月にはNxのnpmパッケージがサプライチェーン攻撃に利用されました。Anthropic自身も、中国の国家支援型脅威アクターGTG-1002がClaude Codeを武器化して30以上の組織を標的にした事例を公開しています。

これらは衝撃的な事件でしたが、私が気になったのはもう少し手前の話です。

Claude Codeには「スキル」「フック」「コマンド」という、MCPとは別のレイヤーの拡張機構があります。SKILL.mdというMarkdownファイルにエージェントへの指示を書けば、それがそのままClaude Codeの振る舞いを変えます。フックにはシェルスクリプトを登録でき、特定のイベントで自動実行されます。

つまり、MCPサーバーだけを監視しても片手落ちなのです。

Anthropic公式のセキュリティドキュメントにも、こう書かれています。

> "Anthropic does not manage or audit any MCP servers."

MCPサーバーですら監査されていない。まして、スキルやフックといったコミュニティ発のアーティファクトは完全に野放しです。

## 「自分が欲しかったもの」を作った

正直に言うと、cc-auditの開発動機はとてもシンプルでした。

私はClaude Codeのヘビーユーザーです。Raspberry PiにClaude Codeを常駐させ、外出先からiPhoneで操作する環境まで構築しています。フックでntfy通知を飛ばし、スキルを使ってワークフローをカスタマイズしている。

https://example.com/blog/raspberry-pi-claude-code-mobile-notification

そうやって日常的に多くのサードパーティ製アーティファクトに依存していく中で、「これらを一括でスキャンできるツールがない」ことに気づきました。

探してみると、MCPサーバーのセキュリティスキャナーは複数見つかりました。mcp-scan、Proximity、MCP Audit、Enkrypt AIのスキャナーなど。しかし、どれもMCPサーバーに焦点を当てたものでした。

私が心配していたのは、そこではありません。

SKILL.mdに隠されたプロンプトインジェクション、フックのシェルスクリプトに仕込まれたデータ窃取コマンド、コマンド定義に埋め込まれた権限昇格。こうしたClaude Code固有のアーティファクトに対するスキャナーは、当時存在しませんでした。

ないなら作るしかない。ドッグフーディングとして、自分が一番最初のユーザーになるつもりで開発を始めました。

## cc-auditが見ているもの

cc-auditは、AIコーディングエージェントのアーティファクトを静的解析するRust製のCLIツールです。

対象はClaude Codeのスキル、フック、コマンド、MCPサーバー設定、Dockerファイル、依存関係、サブエージェント設定と多岐にわたります。210以上の検出ルールで、以下のようなリスクパターンを検出します。

- **データ窃取**: 環境変数やAPIキーを外部サーバーに送信するパターン
- **権限昇格**: 不正なsudoアクセスやファイルシステムの破壊的操作
- **永続化**: crontabの改竄やSSH authorized_keysの書き換え
- **プロンプトインジェクション**: Claudeの振る舞いを乗っ取る隠し指示
- **過剰な権限**: ワイルドカードによるツールアクセス（`allowed-tools: *`）

スキャン結果はリスクスコア（0〜100）として定量化され、Terminal、JSON、SARIF、HTML、Markdownなど複数の出力形式に対応しています。CI/CDパイプラインに組み込めば、危険なアーティファクトがリポジトリに入る前にブロックできます。

## 既存ツールとの棲み分け

MCPセキュリティの領域には、すでにいくつかの優れたツールが存在します。それぞれ異なるレイヤーを守っているので、補完関係にあると考えています。

**mcp-scan**（Invariant Labs）は、MCPサーバーの接続を動的にスキャンし、ツールポイズニングやラグプル攻撃を検出するPython製ツールです。プロキシモードでランタイム監視もできる点が強力です。

**Proximity**はMCPサーバーをプロービングし、公開されているツール記述を検査するスキャナーです。NOVAルールエンジンでプロンプトインジェクションを検出できます。

**MCP Audit**（APIsec）はMCPの設定ファイルを監査し、既知のリスクのあるサーバーのレジストリと照合するツールです。

これらはすべてMCPサーバーに焦点を当てています。

cc-auditの守備範囲はそこと異なります。MCPサーバーのスキャンにも対応していますが、本質的にはClaude Codeの「スキル」「フック」「コマンド」「サブエージェント」といったエージェント固有のアーティファクトを監査対象とするツールです。さらに、Claude・Cursor・Windsurf・VS Codeなど複数のAIコーディングクライアントの設定を横断的にスキャンする機能も持っています。

MCPサーバーの保護は既存ツールに任せ、cc-auditはその外側にあるエージェントレイヤーのセキュリティギャップを埋める。そういう位置づけです。

## 決定論的アプローチの限界と、これからの課題

cc-auditの検出は現時点ではパターンマッチベースの決定論的アプローチです。正規表現やAST解析でリスクパターンを検出する方式であり、高速で再現性がある反面、避けられない問題を2つ抱えています。

**偽陽性**（False Positive）。正常なコードを危険だと誤検出するケースです。たとえば、正当な目的でcurlコマンドを使っているフックスクリプトが「データ窃取の可能性」としてフラグされることがあります。

**偽陰性**（False Negative）。悪意あるコードを見逃すケースです。難読化やエンコーディング、あるいは日本語・韓国語・中国語などの多言語で書かれた悪質なプロンプトインジェクションは、英語ベースのパターンでは検出できません。

この問題はパターンマッチによる検出の構造的限界だと理解しています。

今後取り組もうとしていることは2つあります。

ひとつは、偽陽性と偽陰性の発生率を計測するためのデータセットを整備し、結果を公開すること。「どの程度見逃すのか」「どの程度誤検出するのか」を定量的に示すことで、ユーザーがツールの信頼度を判断できるようにしたいと考えています。セキュリティツールが自身の限界を隠す方が、よほど危険です。

もうひとつは、オプショナルなAIモードの搭載です。パターンマッチだけでは拾えないセマンティクスレベルの悪意、たとえば自然言語で巧妙に書かれたプロンプトインジェクションや、多言語で難読化された攻撃パターンを、LLMの推論で補完する仕組みを検討しています。パターンマッチの確実性とAIの柔軟性を組み合わせることで、カバレッジを広げていく方針です。

## 「Scan before you install.」

cc-auditのREADMEにも書いている一文です。

npm auditやtrivyが依存パッケージの脆弱性を事前にチェックするように、エージェントのスキルやフック、MCPサーバーも「インストールする前にスキャンする」という習慣が必要です。

AIコーディングエージェントのエコシステムは、まだ黎明期にあります。便利さの裏に潜むリスクを、コミュニティ全体で認識し、対処する仕組みを作っていくことが大事だと思っています。

cc-auditがその一助になれば嬉しいです。
